# 设计与维护

## 为什么拆成四个

竞品调研、用户评论、产品定义各有独立的输入、处理过程和交付物。文风横跨业务，可单独润色。一次完整调研可以依次使用这些能力，但不要求每次执行全部流程。

入口保持短：描述触发条件、最小输入、关键步骤、不可破坏的事实边界、何时读取参考文件。68项详细检查保存在各自的 `references/acceptance.md`，案例保存在 `references/examples.md`。从入口直接链接，避免先读总文档再层层查找。

## 指令优先级与迁移

- 用户明确的格式、范围和目标优先于本仓库默认约定。
- 六列评论表、工作文风等是默认工作方法；如果用户给出其他合法格式，保持语义规则并适配输出。
- 产品或场景变化时调整类型枚举，先说明映射，不把硬件评论的分类生硬套到餐饮、教育等无关领域。
- 各Skill能独立交付，不依赖跨Skill隐式调用；跨模块交接传结构化结论和来源，不传全量聊天。
- 不绑定某一种浏览器或文档平台。用户指定平台时使用可用工具；无法读取时报告实际缺口，不伪装采集成功。
- 生成或检查内容不自动授权发布、发信或改写外部文档；按用户任务范围执行。

## 公开内容

验收规则从工作方法抽象得到。案例使用匿名产品及合成原话；标注“原话”仅指案例输入，不代表真实世界评论。例子中的价格、动作和链接不能当成现实产品数据。

不将原始聊天、内部产品定义、私人路径、账号状态、公司文档地址或凭证打包到仓库。公开来源若以后确需引入，应按来源和许可判断可引用范围。

## 迭代方式

1. 记录具体输入、观察到的错误、期待行为，不仅记录“感觉不好”。
2. 区分触发错误、证据问题、流程遗漏、表达问题和用户尚未决定的事项。
3. 在对应Skill改最小必要规则或补一组正反例；不在四个Skill里复制一整套同义规则。
4. 运行结构检查，再用原失败输入和至少一个邻近案例复测。
5. 更新 `docs/validation.md`，分别记录自动校验、Agent试用和人工/平台确认。

不以固定字数、固定结论条数或模型自评分代替实质验收。对来源冲突、模糊语义及产品取舍保留人工例外。

## 扩展新 Skill

在 `skills/` 下增加独立目录和 `SKILL.md`；仅在有实际用途时加入 references、assets或scripts。为新Skill补触发正负例和行为案例，并在marketplace和README登记。仓库根目录是分发集合，不是父Skill。
