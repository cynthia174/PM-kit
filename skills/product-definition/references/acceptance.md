# 产品定义验收

## 使用方式

先检查证据与对象，再检查结构与表达。以下为默认工作约定；用户明确的目标和格式优先。只验本次任务适用项，不为局部任务扩张工作范围。

## 规则

| 规则 | 通过标准 | 失败时处理 / 典型问题 |
| --- | --- | --- |
| D01 定义对象 | 明确设计对象，区分本产品与相关主机、宿主应用、服务的职责 | 把主机配置、外壳或独立计算能力当成本配件的既定需求 |
| D02 决策状态 | 用户确定、证据支持、助手建议、待验证假设分别标清 | 文档写过“建议4—6键”就变成用户硬性要求 |
| D03 目标用户 | 给出具体用户候选及行为/问题特征；与场景分开 | 标题叫目标用户，正文只有“多agent工作”等任务名 |
| D04 场景具体 | 说明处境、当前动作、触发点、障碍与期望结果 | “边看边说”但不清楚看什么、说给谁、哪里看结果 |
| D05 需求有据 | 每个核心需求能回指具体反馈、当前工作问题或明确策略选择 | 只写“根据用户反馈”，没有哪条反馈；用一个围观评论证明全体需求 |
| D06 需求与方案分开 | 需求描述结果，功能描述手段；保留可能的替代方案 | 用户要减少切换，却直接写成“必须有六颗LCD键” |
| D07 任务走通 | 至少一个核心任务说明触发、目标、执行/确认、反馈和失败处理 | “看状态、做审批、说需求”只是一串能力名，没有实际路径 |
| D08 操作对象明确 | 语音发给哪个会话、按钮作用于哪个任务、用户如何确认焦点清楚 | 输入/发送/执行混为一谈；一个停止键含义不明 |
| D09 分类比较 | 比较各分类法回答的问题和局限，并说明选用组合的理由 | 用户要求比较，最后只有一张Kano表或“第三层”一句话 |
| D10 功能映射 | 每个重点模块关联需求；功能可讨论、可拆分、可取舍 | 把全部竞品功能搬进首版；没有理由仍加旋钮和屏幕 |
| D11 粒度合理 | 相同优先级/同一行为链可合写；独立能力需要分别取舍时拆开 | “USB、蓝牙、跨应用、更新”被当成一个不可分功能 |
| D12 期待与排期分开 | 期待标签说明人群和证据，排期另写理由；未知保留假设 | “魅力”自动等于首版；“不做”自动等于用户不感兴趣 |
| D13 同功能不漂移 | 同一功能跨模块、期待标签和优先级保持同一身份，层级不同需解释 | 同项既必备又魅力，却不区分基本可用与进阶体验 |
| D14 首版有理由 | 首版建议有需求、依据、依赖、范围和待定项，不伪装成已确认需求 | 固定4—6键、一旋钮、双模连接，却没有取舍依据 |
| D15 实现边界 | 配件、桌面应用、目标系统、插件分别做什么；必要软件接入条件清楚 | 能接收状态事件就被认为能执行所有控制操作 |
| D16 风险动作清楚 | 批准当前请求、持续放行、取消当前任务、停止多个任务分别定义 | 一律写“审批/急停”；没说明用户如何看待批准内容 |
| D17 形态来自任务 | 桌面、手持、固定空间按相同任务比较输入、结果、确认和姿态 | 先选外观再堆功能；把助手偏好的桌面款写为结论 |
| D18 全章完成度 | 请求的分类比较不遗漏；标题对应内容，编号连续；功能、范围、状态一致 | 已有稿件从“四”跳“六”，却照抄成模板；摘要说已比较实际无内容 |

## 完成判定

- 通过：本次适用项满足，关键结论能回到材料。
- 需修改：有材料可修，先做局部修订并同步受影响结论。
- 待核或待决定：说明具体缺口及影响，不能通过润色或自评分掩盖。

结构检查不能证明事实真实。产品定义的讨论稿通过不代表用户已经确认方案。只汇报发现的问题和重要未决项。
