# 用户评论验收

## 使用方式

先检查证据与对象，再检查结构与表达。以下为默认工作约定；用户明确的目标和格式优先。只验本次任务适用项，不为局部任务扩张工作范围。

## 规则

| 规则 | 通过标准 | 失败时处理 / 典型问题 |
| --- | --- | --- |
| R01 定对象 | 确认评论针对的产品、型号、软件或改装方案；区分买家、围观者、专业评测与问题反馈 | 兼容键盘的做工吐槽被归到原版样例产品A |
| R02 取证据 | 获取具体原文、出处、点赞；按产品和问题选择合适来源，必要时结合官方网站购买页、销售平台、应用评价、社区、视频内容、官方反馈和专业评测 | 只有标题/入口，没有读到评论却生成内容；把官网产品页直接当用户评论 |
| R03 筛相关性 | 留下具体体验、价值判断、替代比较、明确诉求；纯展示/嘲讽/无信息提及可剔除 | “给自己键盘刷固件”被自动视为产品需求 |
| R04 还原语境 | 补清“这种键”“接口”“无线飞鼠”等对象；对可能事实错误的评论结合资料核实 | 猜出来的对象、未查清却说产品没有 |
| R05 拆评价单元 | 一条原话多件事分别成行；不同类型不塞在一个概括里 | 软件卡死、机身易滑、价格不值统一归兼容 |
| R06 保留原意 | 每行原文只对应本行观点，仍保留必要条件；连续摘录或明确省略 | 摘掉否定、拼接句子、把他人观点写成自己使用体验 |
| R07 写概括 | 概括为一个简短可理解的议题；同义说法先统一口径 | 把原文完整重写一次，或缩成读者不懂的暗号 |
| R08 分类型 | 使用六类口径；同一概括尽量同类，涉及不同类先拆 | 协议/蓝牙连接归手感，按键布局归识别错误 |
| R09 判评价 | 好评指被调研对象本身；差评有负面主张；需求有明确愿望或未满足目标 | 替换成替代语音工具才更快，却给原设备记好评 |
| R10 处理提问 | 问题可提示关注点；是否为需求取决于语义；产品是否缺能力另核 | “怎么切换超过6个会话”被直接写成“不支持” |
| R11 同论点去重 | 同产品同论点通常留1—2条代表；保留不同条件/场景的实质差异 | 收几十条“太贵”让声量看起来很大 |
| R12 整理顺序 | 类型相邻、同概括相邻；组内可比点赞降序，无数值项后置 | 全球按赞数混排导致分类散乱；跨平台数值被当统一权重 |
| R13 固定表格 | 每产品一表，固定六列；类型/概括按需合并，其余一一对应 | 多出空列、合并后串行、来源丢失 |
| R14 写单品总结 | 从最终保留的表提炼“总结：＋编号要点”，先说问题/价值，再必要解释 | 仍复述平台、赞数、每条原文；使用“先看结论”长段 |
| R15 删除重复 | 表后只留有用评价入口，不再列单品好评/差评/需求清单 | 表前表后各总结一遍同样内容 |
| R16 补评价入口 | 每产品提供适合本次研究的主要来源入口；官方网站购买页用于确认产品和购买信息，评论/评分/报修/评测等来源分别说明性质 | 把官网商品信息当买家评分；把平台首页当具体评论；自制方案虚构统一评分 |
| R17 写跨产品总结 | 评论部分末尾按好评/差评/需求归纳跨产品主题，不逐产品复述 | 再把每张表的所有行复制一遍 |
| R18 逐点举证 | 每个总总结要点下一段为引用块，注明产品＋具体细节＋对应原话 | 只写“引用：”普通正文，或拿泛来源代替原话 |
| R19 摘要反查 | 结论与当前保留行对应；删评论后同步删/改总结；区分观察、推断、设计建议 | 已删除的价格评论又出现在总结；声称用户已愿付费 |
| R20 全产品回归 | 用户举例纠错必须检查所有产品；最终核对列数、合并、顺序、引用和归属 | 只修样例产品A，后面产品照旧 |

## 完成判定

- 通过：本次适用项满足，关键结论能回到材料。
- 需修改：有材料可修，先做局部修订并同步受影响结论。
- 待核或待决定：说明具体缺口及影响，不能通过润色或自评分掩盖。

结构检查不能证明事实真实。产品定义的讨论稿通过不代表用户已经确认方案。只汇报发现的问题和重要未决项。
