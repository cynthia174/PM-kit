# 评论表字段与分类

## 六列表头

`类型｜概括｜评价｜原文｜点赞｜来源`

每产品一表。底层每行保留六个字段；展示可纵向合并相同类型和概括。原文、评价、点赞与来源分别对应，不因合并丢失映射。

| 字段 | 口径 |
| --- | --- |
| 类型 | 讨论什么问题，不是好坏态度。默认枚举见下表；其他领域可适配。 |
| 概括 | 简短中文，一个可比较的价值、问题或愿望；保留必要对象。 |
| 评价 | 好评、差评、需求。纯信息、购买信号和含糊提问不必硬塞三类。 |
| 原文 | 实际取得的原话，允许相关且语义完整的摘录；译文、补充和推断另标。 |
| 点赞 | 原平台数字或“—”。helpful等口径说明；未知不填0。 |
| 来源 | 可点击的“平台｜具体内容/产品”，优先直达评论、帖子或商品评价。 |

原评论ID、产品型号、证据性质、采集时间、拆分单元ID与总结引用关系可保存在工作底稿，不必增加正文列。数值在拆分行重现只是同一条评论的元数据，不能求和。

## 默认议题

| 类型 | 包含 | 边界 |
| --- | --- | --- |
| 价格 | 贵不贵、值不值、投入回报 | “贵且软件卡死”拆价格和兼容 |
| 语音 | 拾音、识别、响应、近嘴、小声、输入发送 | 麦键布局差归外观，不是识别失败 |
| 替代 | 手机、软件、宏、已有设备的替代价值 | 只有DIY展示且没有比较/诉求时先筛除 |
| 兼容 | 平台、应用、连接、软件稳定性、配置和资源占用 | 协议问题不归外观 |
| 外观 | 形态、布局、握持、按压、防滑、做工、外露结构 | 不限于颜值，合并原手感议题 |
| 功能 | 自定义、快捷操作、会话控制、审批等能力 | 只说“功能少”且不具体，可不收 |

先拆议题，再分类。一个观点可以涉及多个条件，只有独立主张才拆行；不要把因果链拆成失去意义的碎词。

## 展示顺序与去重

类型相邻、同概括相邻；组内可比点赞降序，缺数字后置。不同平台或计数方法不可直接推出谁代表更多用户。代表性以清楚、相关、可核实和信息差异为先。

同产品同论点统一概括后，通常保留1—2条代表；不同场景、版本或失败条件可分别保留。一个评论拆成三行仍是一位评论者的一条样本。

## 总结与引用

单品：标题 → “总结：”编号要点 → 表 → 商品评价入口。不要重复在表后列好评/差评/需求。入口说明是买家评价、问题反馈还是专业评测，首页不充当评论证据。

跨产品：在模块末尾按好评、差评、需求归纳，每点下一段引用具体产品细节和原话。Markdown用引用块，飞书等使用原生组件。引号内只放真正摘录，转述不伪装原文。

总结不得使用已失效或删除后未保留的依据。没有正面样本不制造平衡；“未收集到”不等于“没有人喜欢”。付费意愿、代表性和优先级需要额外验证。
