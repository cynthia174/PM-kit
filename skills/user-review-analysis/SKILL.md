# 用户评论分析

目标是从原话中得到可核查的体验和需求，而不是把每一句提及产品的话都装进表格。

## 按任务读取

- 开始处理表格前读取 [字段与分类](references/table-contract.md)。
- 输出新章节时使用 [评论模板](assets/review-template.md)；用户有明确格式时适配。
- 处理混合评价、替代产品或模糊提问时读取 [正反例](references/examples.md) 的对应案例。
- 交付或验收前读取 [验收标准](references/acceptance.md)。

## 执行

1. 明确每条评论针对的产品、型号、软件或改装方案；区分买家使用、围观、评测、报修与项目展示。不能把兼容版评价算给原版。
2. 保存原话、具体来源、点赞口径和原评论身份。只有页面入口而没有实际文字时，不生成评论。若用户限定只用给定资料，不擅自补网上内容。
3. 筛掉无具体体验、比较或诉求的牵强样本；遇到“这种键”“接口”等指代，结合上下文补清。查不清则隔离为待核，不脑补。
4. 拆出独立评价单元。一条原话同时谈软件、按压和价值应拆行；各行仅摘相关且语义完整的原文。拆行不能增加用户样本数。
5. 写简短中文概括，再分别判断议题类型和好评/差评/需求。同论点统一概括；保留不同场景和条件，避免过度合并。
6. 同产品同论点通常留1—2条代表，优先清楚、相关、可核查的证据，再参考点赞。按类型/概括分组，组内可比点赞降序；缺数字项后置，不跨平台推导需求规模。
7. 默认每产品一张六列表，表前“总结：”加编号要点，表后保留有效商品评价入口。不要再生成表后好差评重复清单。
8. 完整章节末尾跨产品按好评、差评、需求归纳，每条下一段附产品细节和原话引用。仅改单行时不扩写整章。总结只引用当前有效证据，删明细后同步更新总结。
9. 对所有产品类推本次纠错，复核原话、归属、列映射和总结。外部来源未重验时明确范围。

## 关键边界

- 换了别的工具才更好用，不算原产品好评；可支持未满足需求。
- 提问不证明功能缺失；售罄不是功能需求；纯DIY展示不自动证明差评。
- 好评/差评/需求不必强行覆盖每个产品。缺样本不代表没有这种体验。
- 原文列不能放助手润色、翻译或补查的事实；必要解释放概括或注释。
- 不把点赞、拆分行数或围观倾向当成购买意愿与市场比例。
- 默认六类面向产品体验；其他领域允许按任务调整议题，但需明确口径。

## 交付

默认表头：`类型｜概括｜评价｜原文｜点赞｜来源`。底层每行完整；飞书等展示支持纵向合并时再合并类型/概括。引用使用平台真实引用格式，Markdown使用`>`。

验收反馈：`产品/行｜规则ID｜原文依据｜拆/合/删/改/补证｜状态`。确定可修的问题先改；语义、来源和产品归属争议交回人工。不得宣称格式检查证明评论真实。
